> **起草日期**:2026-08-03
> **分支**:`pid-Fback`
> **状态**:待 review / 待启动 / ⚠️ **2026-08-05 新增流程 bug 前置(§二·五,必先做)**

> **目的**:把已验证的反解能力接进 IterationChain,跑通"导入BBL→反解P→出CLI→换参飞→导入下一轮→曲线对比"端到端产品闭环。
> **⚠️ 2026-08-05 审查修正**:原计划前提"流程已通、纯拼胶水"**不成立**。迭代导入流程本身有多曲线污染 + `isIterationMode` 状态串扰 bug,必须**先修流程(新阶段0)再接反解**,否则反解画到错的历史虚线、CLI 对应错轮次。

## 一、为什么是当前最高优先级

- **方向已验证**:2m 怪象3.5寸1505 新飞机,飞手升P(45→49)反解识别为最高 → 迭代闭环"方向正确性"在真实数据上数学成立。
- **精度够用**:FF=0 干净数据 S2/S4 平均 **2.55%**(优于 2g 吴bbl 8.9%)。
- **单次反解再打磨是边际收益**;真正能验证产品形态的是端到端跑通链路。
- **核心算法零风险**:反解器、质量门、CLI 生成、IterationChain 存储**全部已就绪**。
- ⚠️ **但流程本身有 bug(2026-08-05 审查发现)**:迭代导入时"多曲线污染" + `isIterationMode` 状态串扰(1998/2660 多处设置)。**原"拼胶水"前提不成立,必须先修流程(新阶段0)再接反解**——否则反解结果画到错的历史虚线上、CLI 对应错轮次,bug 更难定位(分不清是反解算错还是流程画错)。详见 §二·五。

## 二·五、🎯 UX 流程重构:用户主动方案制(2026-08-05 方向升级,**必先做**)

> 🔑 **方向升级**:原以为是"修流程 bug",深挖后发现根因是 **UX 操作流程从没被设计过**。这不是 patch,是补做本该先做的 UX 设计。原"三层根因诊断"作为代码层证据保留在下方。

### 真正的根因(不是 bug,是缺设计)
- **1.1 以前**:一次曲线绘制 = 严格 1对1,不依赖任何聚合键 → **不出错**。
- **1.1 之后**:**没做 UI 流程计划就开工**,随手让程序"自动按 craftName 把多次 BBL 聚合对照" → 数据张冠李戴。没数据库、没 model、自动猜测 = 错乱温床。
- **用户实测反馈**:"导入第二次 BBL 就崩/参数对不上" + "生成 3/4/5/6 条莫名其妙的曲线"。

### 🔑 craftName 从根上就不该当聚合键(3 硬伤)
| 硬伤 | 实锤 |
|---|---|
| 不稳定 | 飞手随时在 CLI 改 `name`,同一架飞机改名 = 历史断链、查不到 |
| 一架多目标 | 同架飞机休闲/竞速/航拍 PID 完全不同,堆一池互相污染 |
| 会空/重名 | 项目记忆 `wu-bbl-aircraft-mapping` 实测:6 条 bbl 的 craftName **全空**,真实区分靠 board info + 固件 build → 空名崩或全堆一起 |

### 三层数据心智(现在混在一起)
```
飞机档案(慢变: board/电机KV/尺寸/K_plant)
  └── 方案/迭代链[多条](一次调参任务: 基线→收敛)
        └── 飞行记录[多轮](单次 BBL Session)
```
聚合方向应 = 飞机 → 多方案 → 多轮记录,不是 `craftName → 所有记录一锅炖`。
🔑 **重要发现**:`IterationChain` 主键**已经是 `chainId`(UUID)**,craftName 只是属性 → **数据模型方向早对了**,毒只在 `loadTuningHistory` craftName 兼容回退 + 旧 `PIDTuningHistoryManager`。

### 🔑 解法:左右隔离(默认独立 + 用户主动合并)

**核心铁律:默认独立(不拉任何历史),只有用户主动点"加入方案/新建方案"才进方案模式。**

```
┌─────────────────────────────┐
│  首页:方案列表               │
│  ┌─ 方案-001 (3轮,未收敛) ─┐ │
│  ├─ 方案-002 (已收敛)      ─┤ │
│  └─ 方案-003 ...           ─┘ │
│                               │
│  [+ 新建方案]   [🔍 独立分析] │
└──────┬──────────────────┬─────┘
       │ 左路(新逻辑)     │ 右路(回退1.1干净版)
       ▼                  ▼
┌──────────────┐   ┌──────────────────┐
│ 方案工作台    │   │ 独立分析页        │
│ (有 chainId) │   │ (无 chainId)      │
│ isIter=YES   │   │ isIter=NO         │
│ 新逻辑       │   │ = 1.1 前 1对1     │
│ 见下方界面A  │   │ 旧逻辑零改动稳定  │
└──────────────┘   └──────────────────┘
                          │
                   底部 [加入方案](可选)
                          │ 弹:新建/选已有/丢弃
                          ▼
                   加入后跳到「方案工作台」(左路)
```

🔑 **左路 = 新方案逻辑;右路 = 回退到 1.1 前的干净 1对1(旧逻辑零改动,稳定)。** 两路用 `isIterationMode` 开关隔离,互不污染。

**界面 A · 方案工作台(改造现有 `PIDAnalysisViewController`,不新建 VC)**
```
┌─────────────────────────────────────┐
│ ‹ 返回   方案-001 · 第3轮 · 未收敛   │ ← 顶栏(仅方案模式显示)
├─────────────────────────────────────┤
│         [曲线对比图]                 │
│   基线(第1轮,实线) vs 当前(实线)    │ ← 默认只画2条(历史虚线折叠)
│         预测虚线(推荐CLI)            │
├─────────────────────────────────────┤
│  当前 PID:  P 49 / I 85 / D 44      │
│  推荐 CLI:  set p_roll=52 ...       │
├─────────────────────────────────────┤
│      [ 📥 导入本次飞行 BBL ]          │ ← 唯一动作入口
└─────────────────────────────────────┘
        │ 选 BBL → 解析 N Session
        ▼  就地 sheet(不跳页)
┌─────────────────────────────────────┐
│  本次 BBL 含 3 个 Session,合并哪个? │
│  ┌─ Session 1 (00:32) ─────────────┐ │
│  ├─ Session 2 (01:15) ─────────────┤ │
│  └─ Session 3 (02:08) ─────────────┘ │
│  [合并到本方案] [另立新方案] [丢弃]   │
└─────────────────────────────────────┘
```

**数据时序(chainId 什么时候动)**
| 时刻 | chainId | isIterationMode | 行为 |
|---|---|---|---|
| 进独立分析页(右路) | nil | NO | 不查 craftName、不拉历史、不画虚线 |
| 点"加入方案"→新建 | **生成** | YES | 本次分析作第1轮存入 |
| 工作台"导入下一轮" | 不变 | YES | 解析 Session,等用户选 |
| 点"合并到本方案" | 不变 | YES | 当前 Session 作第 N+1 轮存入 |
| 点"另立新方案" | **新生成** | YES | 当前 Session 另起一条链 |
| 点"丢弃" | 不变 | 回 NO | 不存 |

🔑 **关键洞察(三合一)**:砍 craftName 回退 = 让右路回到 1.1 前稳定态 = 跟左路用 `isIterationMode` 开关隔离,**三件事是同一件事**。砍完右路就是干净 1对1,左路是新方案逻辑,**不存在"为了左路动右路"**。

### 代码层根因诊断(已核实 `PIDAnalysisViewController.m`,保留作证据)
- **层 1 · 图表设计本来画多条**(行 1376-1419)— feature:蓝低输入+橙高输入+历史虚线(最多5)+绿色预测 = 最多 8 条。
- **层 2 · 🔑 真 bug — `loadTuningHistory` 兼容回退**(行 2044-2048):`[mgr recordsForCraft:self.currentCraftName]` 按 craftName 拉旧历史 = "3/4/5/6 条虚线"元凶 + "第二次导入参数对不上"根因(旧历史 PID 被当当前参数)。
- **层 3 · 链膨胀**(行 2648 `saveCurrentRecordToChain`)— append 越多,下次画越多虚线。

### 4 屏可交互原型(动 iOS 前先验证流程)
状态机多分支(独立↔工作台↔Session选择↔合并/另立/丢弃),ASCII 表达不了"点按钮跳哪、数据怎么走"的手感 → 出 HTML 可点原型先点一遍。
| 屏 | 验证什么 |
|---|---|
| 1. 方案列表首页 | "新建方案/进方案/独立分析"三入口泾渭分明 |
| 2. 独立分析页 | 1对1 干净,底部"加入方案"可选 |
| 3. 方案工作台 | 顶栏方案状态 + 基线vs当前两条线 + 导入按钮 |
| 4. Session 选择 sheet | 多 Session 就地列,合并/另立/丢弃三选项 |

套现有 app 视觉(零翻译损耗),聚焦"点得动、跳得对",不搞花哨。

### ✅ 已定默认决策(2026-08-05)
1. 首页**保留"独立分析"入口**(快速看一眼不建方案,符合 1.1 前习惯)
2. 历史虚线**默认折叠**(工作台只显"基线 vs 当前"两条最清晰,迭代轨迹按需展开)

### 验证方式
❌ **不必真飞**。历史 BBL(2m 的 1505 4-session、吴 bbl 6 条)在模拟器模拟"导入→选Session→合并→再导入"完整迭代 2-3 轮,反复触发多曲线场景确认修对。项目既有验证模式(2l/2m 都这么干)。

## 六、K 预标定向导 UX(三选一,待定)

#27 K欠定 → 飞手第一飞不知 bestK。最小可行解:**每架飞机预标定一次 K**,存飞机档案(craftName → K_plant)。2m 已证 K-P 无耦合、K 是稳定机械常数。
