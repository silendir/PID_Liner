# CimbarDecoder 断言崩溃修复 — 交接文档

> 2026-08-24 · QRCodeTransfer 分支 · R1b 收尾遗留问题
> 背景:真机( iOS < 17 )启动即崩 + 构建警告两处隐患。当前 App 已用**临时桩**跑通,
> 本文档描述**根治方案**,交给新会话执行。

---

## 一、问题清单(两个,同源)

### 问题 1:dyld 启动崩溃 `Symbol not found: __ZNSt3__122__libcpp_verbose_abortEPKcz`

**崩溃现场**(真机启动时):

```
dyld[71617]: Symbol not found: __ZNSt3__122__libcpp_verbose_abortEPKcz
  Referenced from: .../PID_Liner.app/PID_Liner
  Expected in: /usr/lib/libc++.1.dylib
```

**根因链**:

1. 解 mangled 名:`std::__1::__libcpp_verbose_abort(char const*, ...)` —— 这是
   **libc++ hardening(强化模式)的断言失败报告函数**,由 LLVM 15+ 的 libc++ 头引入。
2. OpenCV 4.14 源码内置的 **kleidicv**(SIMD 加速库,`3rdparty/kleidicv`)在编译时
   带上了 libc++ hardening 断言,其两个目标文件引用了该符号:
   - `kleidicv_hal.o`
   - `kleidicv_thread.o`
3. 该符号只在 **iOS 17+** 的系统 `libc++.1.dylib` 里导出;App 链接目标
   `arm64-apple-ios16.2`,真机系统 < iOS 17 → dyld 启动即崩。

**定位手段**(复现时可用):

```bash
FW=PID_Liner/PID_Liner/Libs/CimbarDecoder.xcframework
for f in $(find "$FW" -name "*.a"); do
  nm "$f" 2>/dev/null | grep -q "__libcpp_verbose_abort" && echo "HIT: $f"
done
# 进一步定位到目标文件:
nm -A "$FW/ios-arm64/CimbarDecoder-device.a" | grep "__libcpp_verbose_abort"
# → kleidicv_hal.o / kleidicv_thread.o 为 U(未定义引用)
```

### 问题 2:OpenCV 子构建部署版本失控(warning,上架隐患)

**构建日志**:

```
ld: warning: object file (...CimbarDecoder-device.a[N](xxx.o))
was built for newer 'iOS' version (26.5) than being linked (16.2)
```

**根因**:`技术验证Demo/cimbar-ios-build/build-cimbar-ios.sh` 传了
`-DIPHONEOS_DEPLOYMENT_TARGET=13.0`,但 **kleidicv/OpenCV 部分 CMake 子目录
没有透传该变量**,实际用了 SDK 26.5 当最低版本。当前仅 warning 能跑,
但:① 上架审核可能被拒(LC_VERSION_MIN 高于声明);② 低版本系统上有潜在的
指令集/API 可用性风险。

## 二、当前临时桩(已在跑,勿重复修)

| 位置 | 内容 |
|---|---|
| `PID_Liner/PID_Liner/libcpp_verbose_abort_stub.cpp` | App target 内的桩定义(文件系统同步组自动编译),链接时排在 `-lc++` 之前,符号绑定到本地,不再查系统 libc++ |
| `技术验证Demo/cimbar-ios-build/libcpp_verbose_abort_stub.cpp` | 同源文件(构建层留档) |
| 两份 `.a` 里注入的 `stub_dev.o`/`stub_sim.o` | `ar r` 塞进去的,现已冗余(永远不会被链接器拉起),重建 xcframework 后自然消失 |

⚠️ 桩的语义 = 打印消息 + abort,与上游断言行为等价,**不是数据完整性风险**;
问题是它"掩盖"而非消除——正确做法是让 OpenCV/kleidicv 编译时就不产生该引用。

## 三、根治方案(交给新会话执行)

### Step 0:恢复 OpenCV 源码(如 /tmp/opencv 已被清)

```bash
# 构建脚本默认 OPENCV_SRC=/tmp/opencv,OpenCV 4.14.0(仓库 submodule/原始来源见 build 脚本注释)
# 磁盘紧张时可下到别处:export OPENCV_SRC=/path/to/opencv
```

### Step 1:关 hardening + 强制部署版本透传

改 `技术验证Demo/cimbar-ios-build/build-cimbar-ios.sh`,
在两个 `cmake -S "$OPENCV_SRC" ...` 调用里加:

```bash
-DOPENCV_ENABLE_LIBCPP_HARDENING=OFF \
-DCMAKE_CXX_FLAGS="-D_LIBCPP_HARDENING_MODE=_LIBCPP_HARDENING_MODE_NONE" \
-DCMAKE_C_FLAGS="-D_LIBCPP_HARDENING_MODE=_LIBCPP_HARDENING_MODE_NONE" \
```

> 若 OpenCV 的 CMake 没有 `OPENCV_ENABLE_LIBCPP_HARDENING` 这个开关(版本相关),
> 直接靠 `CMAKE_CXX_FLAGS` 宏定义即可(硬汉模式宏对 kleidicv 的 C++ 单元生效;
> kleidicv 纯 C 单元不受影响)。

部署版本透传,追加到两个 cmake 调用(已有 `-DIPHONEOS_DEPLOYMENT_TARGET` 的
检查为何没生效——kleidicv 子目录可能用了独立的 `CMAKE_OSX_DEPLOYMENT_TARGET`):

```bash
-DCMAKE_OSX_DEPLOYMENT_TARGET=16.2 \
```

并 `export IPHONEOS_DEPLOYMENT_TARGET=16.2`(脚本现在 export 13.0,与主工程
实际 link target 16.2 不一致,统一成 16.2;若主工程 Podfile 是 13.0,则以
`xcodebuild -showBuildSettings` 查到的 `IPHONEOS_DEPLOYMENT_TARGET` 为准)。

### Step 2:重建 xcframework

```bash
cd 技术验证Demo/cimbar-ios-build && bash build-cimbar-ios.sh all
# 产物: dist/CimbarDecoder.xcframework
```

### Step 3:替换 + 删桩验证

```bash
rm -rf PID_Liner/PID_Liner/Libs/CimbarDecoder.xcframework
cp -R 技术验证Demo/cimbar-ios-build/dist/CimbarDecoder.xcframework PID_Liner/PID_Liner/Libs/
# 删 App 内桩(根治后不再需要;先删再验证,若删了又崩说明 Step 1 没生效)
rm PID_Liner/PID_Liner/libcpp_verbose_abort_stub.cpp
```

### Step 4:验证判据(全部满足才算修复完成)

```bash
# ① 新 .a 不再引用断言符号(无输出 = 通过)
nm PID_Liner/PID_Liner/Libs/CimbarDecoder.xcframework/ios-arm64/CimbarDecoder-device.a | grep "__libcpp_verbose_abort"
# ② 部署版本警告消失(构建日志里 grep 不到 "built for newer 'iOS' version")
xcodebuild -workspace PID_Liner/PID_Liner.xcworkspace -scheme PID_Liner \
  -destination 'generic/platform=iOS' build 2>&1 | grep "newer 'iOS' version"
# ③ 编译通过
# ④ 真机(iOS<17)启动不崩 + 扫码接收端到端可用(cimbar.org 发小文件,进度到 100%)
```

### Step 5:收尾

- 若验证全过:删两份 .a 里的旧 stub 注入已随重建消失,无需处理;
  commit 信息建议 `R1b-fix: OpenCV/kleidicv 关 libc++ hardening + 部署版本透传,根治 verbose_abort 崩溃`
- 若 `OPENCV_ENABLE_LIBCPP_HARDENING=OFF` 无效:读
  `$OPENCV_SRC/3rdparty/kleidicv/CMakeLists.txt`,找它设置 hardening 的行,
  针对性覆盖(或 `-DKLEIDICV_...=OFF`,以实际 CMake 选项名为准)。
