## 一、🔑 核心结论(先读这段)

1. **iPhone 原生 App 完全能连**——`CoreBluetooth` 是苹果给原生 App 的蓝牙驾照(网页没驾照,所以 BF web 在 iPhone 不行,但我们 App 行)。
2. **SpeedyBee BT 模块 = BLE-串口桥**——飞控端看到的是普通 UART MSP(115200),BT 模块把串口字节流包成 BLE 特征值传输。**MSP 帧格式与 USB 串口版完全一致**,没有 BLE 专属包袱。
3. **8 种市面 BT 模块 UUID 全已知**(BF Configurator Android 源码直查)——一次性支持 SpeedyBee V1/V2、HM-10/11、CC2541、HC-05、DroneBridge、Nordic NUS。
4. **黑盒下载命令链已挖全**:`MSP_BLACKBOX_CONFIG` / `MSP_SET_BLACKBOX_CONFIG` / `MSP_DATAFLASH_SUMMARY` / `MSP_DATAFLASH_READ`。
5. **🔑 移植完整性判定(2026-08-03 补):"连接飞控"+"下载 BBL"两个核心指令 = 100% 可完整移植,零协议猜测。** 8 个本地参考文件覆盖了从 BLE GATT 操作 → MSP 帧编解码(v1 XOR + v2 CRC8-DVB-S2)→ 字节流状态机重组 → dataflash 分块协议的全链路,逐字节都有 BF 工程师写好的实现可对照。移植本质 = JS/Java → ObjC 的 API 翻译,不是协议逆向。
6. **🔑 raw flash dump = .bbl 字节流(2026-08-03 落实):`BlackboxDecoder.xcframework` 零改复用坐实。** 直查 `MSPHelper.js:2545-2615` 的 `dataflashRead`——BF 自己就是把每个 chunk 的 `compression==0` 原始字节(`DataView` 跳过 7 字节头)直接拼起来当 `.bbl` 文件落盘,**中间没有"flash→.bbl 封装层"**。所以我们读回的字节拼成文件,直接喂现成解码器即可,无需任何格式转换。
7. **⚠️ "能直接开工不重写"是过度乐观(2026-08-03 修正):协议层能抄,但 5 个工程层未知点必须先验证。** 见 §十一 完整清单。协议帧/UUID/命令码确实齐了照抄即可;但 Huffman 是否强制、UUID 实测匹配、MTU+写流控、v1/v2 协商、错包重试这 5 个 BT 专属坑,抄不到、必须实测。直接写完整版 = 大概率写到一半返工。**正确节奏:阶段 0 协议层单测(2-3天,零硬件)→ 阶段 1 真机 POC(2-3天,SpeedyBee F7 Mini 已就绪)跑通最小链路 → 再进阶段 2 写完整下载 UI。见 §九 三阶段分层(复刻反解验证模式)。**

## 五、🔑 MSP 帧格式(v1 + v2)

MSP 帧 = BLE 特征值的 payload。FC 收到 Write 特征值的字节流后,按 MSP 帧解析。**与 USB 串口版完全一致**(BT 模块只是透明传输)。

### 5.1 MSP v1(小 payload,≤255 字节)

```
$ M <direction> <size> <cmd> <payload...> <checksum>
$  = 0x24 ('$')
M  = 0x4D ('M')  -- v1 标志
direction = 0x3C ('<') 发 / 0x3E ('>') 收
size      = 1 字节(payload 长度,0-255)
cmd       = 1 字节(命令码,如 MSP_DATAFLASH_READ=71)
payload   = size 字节
checksum  = 1 字节 XOR(size ^ cmd ^ payload[0..n])
```

### 5.2 MSP v2(大 payload,BF 4.x 必需,>255 字节)

```
$ X <direction> <0x00> <size:2 LE> <cmd:2 LE> <payload...> <checksum:1>
$  = 0x24
X  = 0x58 ('X')  -- v2 标志
direction = 0x3C / 0x3E
0x00       = flag 字节(预留)
size       = 2 字节 LE(payload 长度,可达 65535)
cmd        = 2 字节 LE(命令码)
payload    = size 字节
checksum   = 1 字节 CRC8-DVB-S2(覆盖 flag+cmd+payload,算法见 5.4)
```

🔑 **dataflash 大块读取必须用 v2**(单块 >255 字节)。BF 4.3.1(我们手头新飞机固件)支持 MSP v2。

### 5.3 🔑 校验和算法(直查 `msp.js`,iOS 1:1 移植)

**v1 校验和 = XOR**(单字节,`msp.js:242-248`):

```c
// ObjC 等价(伪码)
uint8_t checksum = 0;
checksum ^= size;            // 注意:v1 size 是 1 字节
checksum ^= cmd;
for (b in payload) checksum ^= b;
// 附加到帧尾
// 特例:size==255 表示 jumbo 帧,额外读 2 字节真实长度(JUMBO_FRAME_MIN_SIZE=255, msp.js:23)
```

**v2 校验和 = CRC8-DVB-S2**(单字节,多项式 0xD5,`msp.js:319-328`):

```c
// ObjC 等价(逐字节,msp.js:319-328)
uint8_t crc8_dvb_s2(uint8_t crc, uint8_t ch) {
    crc ^= ch;
    if (crc & 0x80) {
        crc = ((crc << 1) & 0xff) ^ 0xD5;   // 多项式 0xD5
    } else {
        crc = (crc << 1) & 0xff;
    }
    return crc;
}
// 用法:从 crc=0 开始,依次喂 flag → cmd 低 → cmd 高 → payload 每字节
//msp.js:253-267 验证 v2 帧时按同样顺序计算
```

🔑 **iOS 移植要点**:这两个函数加起来 ~15 行 C/ObjC,可直接照搬(算法是数学事实,无 license 问题)。v1 用 XOR,v2 用 CRC8-DVB-S2,别搞混。

### 5.4 🔑 字节流状态机重组(`msp.js:89-285` 整段)

BLE notify 是无边界字节流(一帧可能跨多个 notify 包,一个 notify 也可能含多帧)。`msp.js` 用状态机逐字节吃:

```
IDLE           → 收 0x24('$') → PROTO_IDENTIFIER
PROTO_IDENTIFIER → 收 0x4D('M') → DIRECTION_V1 路径
                 收 0x58('X') → DIRECTION_V2 路径
DIRECTION_*    → 收 0x3C('<' 发) / 0x3E('>' 收) → PAYLOAD_LENGTH
PAYLOAD_LENGTH_V1 → 1 字节 size(若==255 进 JUMBO 读额外 2 字节)
PAYLOAD_LENGTH_V2  → 2 字节 LE size
CODE           → 读 cmd(v1:1 字节;v2:2 字节 LE)
PAYLOAD        → 读 size 字节到 buffer
CHECKSUM       → 读 1 字节,与本地计算的校验和比对 → 匹配则交付一帧
```

🔑 **iOS 实现**:`didUpdateValueForCharacteristic:` 把收到的 `NSData` 字节逐个喂给状态机实例(同 msp.js 的 `read()`),状态机吐出完整帧再交给 `MSPClient` 处理。这是整个协议层最容易写错的地方,**务必对照 `msp.js:89-285` 逐分支译**。

### 5.5 BLE 分包重组补充

一个 MSP 帧可能跨多个 BLE notify 包到达(BLE MTU=247,扣除头实际 ~244 字节/包)。BF Android 在 `onCharacteristicChanged`(`BetaflightBlePlugin.java:740` 附近)里把字节转交给上层状态机(`msp.js`)切分。iOS 侧 `didUpdateValueForCharacteristic:` 同理——把字节灌进 §5.4 的状态机即可,状态机自然处理跨包帧。

```javascript
function dataflashRead(address, blockSize, onDataCallback) {
    let outData = [
        address & 0xff, (address >> 8) & 0xff,       // address: U32 LE(读起始地址)
        (address >> 16) & 0xff, (address >> 24) & 0xff,
    ];

        blockSize & 0xff, (blockSize >> 8) & 0xff,   // blockSize: U16 LE(本次读多少字节)
    ]);
    outData = outData.concat([1]);                    // allowCompression: U8(1=允许压缩)
    MSP.promise(MSP_DATAFLASH_READ, outData).then(...);
}
```

### 7.4 🔑 三条错误/重试路径(`MSPHelper.js:2598-2612`,必须翻译)

`dataflashRead` 的 Promise 不是只走 happy path,BT 偶发错包是常态,**不翻译这三条路径,下载半路必崩**:

```javascript
// 路径 A:地址不匹配(2598-2602)——飞控返回的 chunkAddress != 请求的 address
if (chunkAddress != address) {
    console.log(`Expected address ${address} but received ${chunkAddress} - retrying`);
    onDataCallback(address, null);  // 返回 null → 调用方强制 retry 同一地址
}

// 路径 B:CRC 错(2605-2609)——校验和不过(BT 干扰/CC2541 损坏)
(error) => {
    if (error instanceof MspCrcError) {
        console.log(`CRC error for address ${address} - retrying`);
        onDataCallback(address, null);  // 同样强制 retry
    }
}

// 路径 C:超时/取消(2610-2612)——真出错,上抛
    else {
        onDataCallback(address, null, null, error);  // 第 4 参 = error,终止下载
    }
```

🔑 **iOS 实现**:`MSP_DATAFLASH_READ` 循环里,回调收到 `null` 数据时**重发同一 address**(带重试计数,超过 N 次走路径 C 上抛)。下载循环必须是"地址驱动"而非"序号驱动",这样断点续传和重试共用同一套逻辑(记 `lastAddress`,重连/重试都从 `lastAddress` 继续)。

### 7.5 ⚠️ Huffman 解压的隐藏依赖(若 `allowCompression=0` 飞控不尊重)

`MSPHelper.js:2551` BF 硬编码 `allowCompression=1`。MVP 我们想 `allowCompression=0` 跳过解压——**但没实测过飞控尊不尊重这个请求位**。若飞控强制返回 `compressionType=1`,必须移植(`MSPHelper.js:2571-2588`):

```javascript
const compressedCharCount = response.data.readU16();   // 额外 2 字节伪头(未压缩字节数)
const compressedArray = ...;                             // dataSize - 2 字节
const decompressed = huffmanDecodeBuf(
    compressedArray,
    compressedCharCount,
    defaultHuffmanTree,      // ⚠️ BF 固件源码常量,不在我们 8 个 JS 文件里!
    defaultHuffmanLenIndex,  // ⚠️ 同上
);
```

🚨 **关键**:`defaultHuffmanTree` + `defaultHuffmanLenIndex` 这两棵 Huffman 常量树在 **BF 固件源码** `blackbox/blackbox_encoding.c` 里,**不在当前 8 个 Configurator JS 文件里**。如果 POC 实测飞控强制压缩,需另下一份固件源码抄常量。

→ **POC 验证优先级最高**:第 2 天就读一小段,确认 `allowCompression=0` 是否被尊重。被尊重 = 省一大块工作;不尊重 = 必须移植 Huffman。

### 7.6 响应头格式(7 字节)

| 偏移 | 字段 | 类型 | 含义 |
|---|---|---|---|
| 0–3 | address | U32 LE | 本块数据对应的 flash 地址 |
| 4–5 | dataSize | U16 LE | 本块数据字节数(不含头)|
| 6 | compressionType | U8 | 0=原始, 1=Huffman |
| 7+ | data | bytes | `dataSize` 字节 BBL 数据 |

### 7.7 🔑 下载循环(写进 .bbl,地址驱动)

```
1. MSP_DATAFLASH_SUMMARY → 拿 usedSize(总下载量)
2. address = 0, retryCount = 0
3. while address < usedSize:
     blockSize = min(4096, usedSize - address)   // 每次读 4KB(BLE 慢,块不宜过大)
     发 MSP_DATAFLASH_READ(address, blockSize, allowCompression=0)   ← MVP 用 0(原始),跳过 Huffman
     等响应回调:
       · chunkAddress == address 且 data != null → 取 dataSize 字节 → 追加写入 .bbl → address += dataSize → retryCount=0 → 更新进度条
       · data == null(路径 A 地址错 / 路径 B CRC 错)→ retryCount++ → 重发同一 address(不前进)→ 超过 N 次 → 走路径 C 上抛
       · error(路径 C 超时/取消)→ 终止,记录 lastAddress 进 IterationChain,重连后续传
4. .bbl 完成 → 喂 BlackboxDecoder.xcframework(已有,零改动)→ raw flash = .bbl 字节流,无封装层(见 §一 结论 6)
```

🔑 **MVP 关键决策**:`allowCompression=0`——请求原始数据,跳过 Huffman 解码(省去移植 `huffmanDecodeBuf` + `defaultHuffmanTree` 的工作量)。代价:传输量略增。**前提**:POC 实测飞控尊重这个请求位(见 §7.5)。不尊重则必须回到 Huffman 路径。

🔑 **地址驱动 vs 序号驱动**:循环用 `address` 推进而非"第 N 块",这样断点续传和重试共用同一逻辑——记 `lastAddress`,重连后 `address = lastAddress` 继续。不额外维护"已下载块号"状态。

⚠️ **BLE 吞吐现实**:BLE 实际速率 ~10-30 KB/s(受 MTU/连接间隔限制)。8MB 满录的 flash 下载约 **5-15 分钟**。UI 必须有进度条 + 断线续传(记 lastAddress,重连后从该地址续)。

## 九、⏱️ effort + 步骤(三阶段分层 · 复刻反解验证模式)

> 🔑 **核心策略**:像反解那样**先在测试目标跑技术验证,再拼进主项目**。BLE 风险比反解更高(5 个工程未知点),分层验证收益更大。前两阶段对主项目**零/最小干扰**,阶段 2 才动主项目,且搬的是已验证代码。
>
> ⚠️ **本质差异(决定怎么分层)**:反解是纯计算,整个能塞进 XCTest;BLE **协议层是计算(可纯单测),传输层必须真机+真硬件**。所以把可纯软件验证的剥离出来先消化,真机部分留到最小 POC。
>
> ✅ **硬件已就绪**:SpeedyBee F7 Mini 到手,阶段 1 可随时启动,不再有"找硬件"隐性前置。

## 十、⚠️ 已知陷阱

| # | 陷阱 | 对策 |
|---|---|---|
| 1 | **BLE 吞吐慢**(8MB 需 5-15 分钟)| 进度条 + 断线续传(记 lastAddress),UI 提示用户保持 App 前台 |
| 2 | **MSP 帧跨包重组** | `NSMutableData` 缓冲 + 按 `$M`/`$X` 帧头切分,别假设一个 notify = 一帧 |
| 3 | **MSP v1 vs v2** | dataflash 大块读必须 v2(>255 字节),BF 4.3.1 支持 |
| 4 | **Huffman 压缩可能强制** | MVP 想 `allowCompression=0` 跳过,但飞控**可能不尊重**。阶段 1 Day 2 必须实测响应头第 7 字节。强制则必须移植 `huffmanDecodeBuf`,且常量树不在 8 个本地 JS 文件里(见陷阱 #11) |
| 5 | **改黑盒配置需解锁态** | armed 时拒绝写,UI 提示"先拔桨断电调" |
| 6 | **多 BT 模块兼容** | 抄全 8 UUID 表,不只 SpeedyBee |
| 7 | **iOS 后台 BLE 限制** | 下载时 App 进后台可能断,需 `state restoration` 或提示保持前台 |
| 8 | **`MSP_DATAFLASH_READ=71` 不是 72** | 72 是 ERASE,网上资料有误,以源码 `MSPCodes.js:50` 为准 |
| 9 | **BF 固件版本差异** | BF 4.3.1 vs 4.5 vs 2025+ 的 MSP API 版本/命令码可能微差,以飞控 `MSP_API_VERSION` 协商 |
| 10 | 🔑 **CC2541/BT-11 桥把校验和损坏成 0xff**(`msp.js:290-294`)| 廉价 BLE 桥模块会破坏 MSP 校验和字节。BF 已写兜底:检测到该型号时覆盖 `crcError=false` 放行。iOS 侧必须复刻此兜底,否则用 CC2541/HM-11 模块会"校验全错、数据看似全废",debug 一周不知为啥。**这是读源码 vs 抓包的本质区别——异常处理只在源码里** |
| 11 | 🔑 **Huffman 常量树不在本地 8 文件里** | `defaultHuffmanTree` + `defaultHuffmanLenIndex` 在 BF **固件**源码 `blackbox/blackbox_encoding.c`,不在已下载的 Configurator JS 文件里。若 POC 实测飞控强制压缩(陷阱 #4 落实),需另下固件源码抄这两棵常量树,否则 Huffman 解压无从下手。**这是 raw flash = .bbl 之外,第二个"看起来齐了其实还差一块"的隐藏依赖** |
