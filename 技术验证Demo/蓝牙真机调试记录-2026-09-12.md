## 一、实现架构（4 个文件）

| 文件 | 职责 |
|---|---|
| `MSPClient.{h,m}` | MSP v1/v2 双版本帧编解码 + 单字节流状态机（帧跨 BLE 包自动重组）。v2 格式照 BF 配置器 `msp.js encode_message_v2`：`$X<flag cmdLE16 lenLE16 payload crc8_dvb_s2`，CRC8-DVB-S2 多项式 0xD5 初值 0，覆盖 flag 起至 payload 末尾 |
| `FCBluetoothService.{h,m}` | CoreBluetooth 单例：按 7 家已知 service UUID 过滤扫描 → 连接 → 同服务内配对"第一个可写+第一个可 notify"特征 → 订阅。发命令（v1/v2）+ 按命令码匹配响应 + 代数核对超时 + 连接 10s 超时兜底 |
| `DataflashDownloader.{h,m}` | `MSP_DATAFLASH_SUMMARY(70)` 查用量 → 循环 `MSP_DATAFLASH_READ(71)`（v2 帧，4KB/块，allowCompression=0）→ 拼成 .bbl 落盘 Documents（`ble_时间戳.bbl`）。进度回调 + 每块重试 1 次 |
| `MassStorageImportViewController.m` | 五态状态机：扫描→连接→已连接（⚡激活 U 盘 + 📡蓝牙直下双按钮）→已激活（插线引导）→导入结果。下载中有进度条，再点取消，失败变 🔁 重新下载 |

## 二、调试时间线与 6 个坑（全部已修，新坑先查这里）

### 坑 1：页面永远停在"蓝牙启动中…"
- **症状**：进蓝牙页后文案不变，扫描不启动
- **根因**：`centralManagerDidUpdateState:` 是空实现。首次进场时权限弹窗未点，`bluetoothReady=NO`；用户点允许后状态变就绪，但**没有任何回调通知页面**，进场那一次检查永远不重跑
- **修复**：`FCBluetoothService` 增加 `onStateChanged(ready, stateText)` 回调，页面订阅后变就绪即重新进入扫描态

### 坑 2：`API MISUSE: can only accept this command while in the powered on state`
- **根因**：蓝牙未就绪时调了 `stopScan`
- **修复**：`startScan`/`stopScan` 入口加 `bluetoothReady` 守卫

### 坑 3：GATT 连上但 MSP 链路全哑（"飞控无响应"）
- **症状**：连接成功，API 探测 5s 超时
- **根因（两个叠加）**：
  1. **跨服务特征混搭**——原"全局第一个可写+第一个可 notify"可能写在 A 服务、听在 B 服务。修复：**同服务内配对**，有"写+通知"齐备的服务整体优先
  2. **写入类型写死 WithResponse**——若特征只支持 WriteWithoutResponse，iOS 直接拒发=无声。修复：自适应（有 Write 属性用 WithResponse，否则 WithoutResponse），同 BF 插件 713-715 行
- **实测**：F7 Mini 的 ABF0 服务 = ABF1(props=6, 写) + ABF2(props=18, 通知) + ABF3/ABF4 备用

### 坑 4：激活成功却报"存储设备未就绪"
- **根因**：`MSP_SET_REBOOT(68)` 响应 payload = `[rebootType, ready]` **两字节，ready 在 [1]**（BF 配置器 `MSPHelper.js:812-821` 实锤）。原代码读 `[0]` 拿到的是 rebootType=2 的回显，2≠1 误判失败。真实回帧 `24 4D 3E 02 44 02 01 45`
- **教训**：用户第二次点激活报"飞控无响应"其实也是成功的旁证——飞控第一次就已重启成 U 盘、蓝牙桥已死

### 坑 5："固件返回压缩数据,暂不支持"
- **根因**：`MSP_DATAFLASH_READ` 请求第 7 字节 allowCompression 照抄配置器传了 1，固件真的回 Huffman 压缩数据（配置器有 `huffmanDecodeBuf` 解码器，我们没有）。BF 固件源码 `mspFcDataFlashReadCommand`（msp.c:2987）确认该字节可选：**传 0 即原始字节，无需实现解码器**
- **修复**：allowCompression=0

### 坑 6：僵尸超时（最隐蔽，险些误判为飞控问题）
- **症状**：分块下载每约 5 秒出现一次"飞控无响应"假失败→重试；后期重试连环风暴，并出现"闪存地址错位"
- **根因**：`dispatch_after` 5s 超时定时器**回包到达后不撤销**。铁证：`17:03:46` 的 `cmd=70` 早已收到响应，其超时 5 秒后引爆，误杀了当时在飞的 `cmd=71`（日志"⏱ cmd=70 无响应"出现在 cmd=71 发出 1ms 后）。僵尸定时器越积越多 → 周期性误杀 → 重试又排新僵尸 → 连环误杀 → 旧地址迟到回包插队 → 地址错位
- **修复**：`requestGeneration` 代数计数，超时引爆时核对代数，不是自己那代就静默作废。另把地址错位从硬失败改为可重试（配置器同款策略）
- **教训**：**长周期轮询协议里，超时定时器必须与请求生命周期绑定**（代数/handle 核对），否则高吞吐时定时器堆积必然互杀

## 三、协议事实速查（真机实测验证）

- 扫描过滤 7 家 service UUID 即可命中 SpeedyBee V2（ABF0）；设备名可能为空，识别靠 UUID
- v1 帧：`$ M < size cmd payload crc8(XOR: size^cmd^payload)`；v2 帧：`$ X < 0x00 cmdLE16 lenLE16 payload crc8_dvb_s2`；响应方向 `>`，命令不支持为 `!`
- `MSP_API_VERSION(1)` 链路探测：F7 Mini 回 `协议0 / API 1.44`（= BF 4.4.x）
- `MSP_SET_REBOOT(68)` + rebootType=2(MSC)：响应 `[2,1]`=成功重启为 U 盘；**MSC 模式断电即退出**，恢复蓝牙需重新上电
- `MSP_DATAFLASH_SUMMARY(70)`：`[flags, sectors u32, totalSize u32, usedSize u32]`；flags&1=ready, flags&2=supported。实测 F7 Mini：8MB 闪存 / 已用 1.47MB
- `MSP_DATAFLASH_READ(71)` 请求 `[addr u32LE][blockSize u16LE][allowCompression u8]`，响应 `[addrEcho u32][dataSize u16][compression u8][data…]`；原始 flash dump 就是 .bbl 字节流（日志已见 `H Firmware type / H Board info` 黑盒头 ASCII）
- BLE 串口桥**同时只允许 1 个 central 连接**——被 SpeedyBee App/电脑 BF 占用时"扫得到连不上"；断电重上电释放
